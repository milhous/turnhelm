## 3. The stdout machine-output contract (SC-1)

Normative definition:

1. **stdout carries at most one worker message: the final agent message.** The supervisor retains the text of the last decoded `message` event (one string, bounded by the existing 1 MiB frame cap; no new limit) and writes it exactly once — `text + "\n"`, through the existing `emitMessage` path with its pending-write accounting — only when the run reaches completed-eligibility as defined in point 4. "Final" is positional: the last decoded agent message across the accepted execution stream wins, including any decoded after a completion event — the decoder enforces no event ordering and `completionSeen` is sticky, and this spec adds no turn-state validation. An absent message and an empty-string message stay distinguishable: absent means no write at all; `text: ""` means stdout is exactly `"\n"`.
2. **Every earlier agent message is discarded.** It is decoded, counted in `progressEvents`, and never written to any sink. Precedent: the child's own stderr is already drained and discarded (`src/codex.ts`), and tool-progress diagnostics are already reduced to fixed-category lines. Progress observability stays what the receipt already projects (`progressEvents`, `lastEventAgeMs`); narration is not evidence.
3. **Emission gating, not transactional delivery.** No write is initiated unless the run has reached completed-eligibility. A run that settles `failed` (turn.failed, nonzero child exit, missing completion, protocol/spawn/stdin/output failure) or `cancelled` before emission therefore writes nothing, whatever messages were decoded. Delivery itself is non-transactional: a caller cancellation or sink error that lands while the final write is in flight may leave some or all of its bytes on stdout while the receipt records `cancelled`/`failed`. Consumers gate on the exit code and the stderr receipt, never on stdout alone — stdout presence proves nothing, since a completed run with zero messages is legitimately empty.
4. **Settlement ordering — an explicit, once-only emission phase.** When `settle()` has satisfied every existing precondition (child close, cleanup obligations discharged, no in-flight writes, no drain wait), it evaluates completed-eligibility — the same status predicate `finish()` computes, shared rather than duplicated — and only an eligible run with a retained final message proceeds to emission: the emission flag is set **before** the sink is invoked (ack re-entries into `settle()` must never re-emit), the write goes through the existing `emitMessage` accounting, and the run then passes through the pending-write/drain gates again before the next `settle()` finishes. Emission precedes `finished = true`, so a write throw, sink error, or close on the final write still fails the run through `recordFailure("output")` exactly as streamed-write failures do today; cancellation keeps its precedence and settles despite an in-flight final write; sink-listener ownership rules are unchanged.
5. **Corollary for consumers:** after a worker start, stdout carries at most one write, initiated only at completed-eligibility; it is empty for zero-message completions and for every failure or cancellation that lands before emission. Success is never inferred from stdout presence — the exit code and receipt remain the only success evidence. The final message is arbitrary content: one message can still carry prose, code fences, or several JSON objects, so strict-JSON oracles keep judging and can still fail. The receipt, the journal, and stderr are byte-for-byte unchanged in shape.

Security and privacy posture: worker-controlled text reaches exactly one sink (stdout), once, instead of an unbounded stream of narration lines. The stderr trust boundary — fixed lines plus one receipt, the boundary the harness's `receiptCount === 1` integrity check depends on — is preserved by construction, since no worker text can appear there. This is still not a redactor: the final message is arbitrary content and the existing "stdout is not a general-purpose redactor" honesty statement stays.

Performance posture: the decode path is unchanged (messages are decoded and counted as today); the only difference is that zero writes occur during the turn and one write occurs at settlement. One additional retained string, already bounded. No new caps, timers, channels, or config keys.
