- 日期：2026-10-10
- 状态：经 Astra 复核修订的草案，规格与执行计划待用户审阅；尚未授权实施
- 代码基线：`891abdd3658c49a63c94500ea502bbf70f2b5efa`
- 用户要求：使用 Node 24，放弃 Node 22.8，基于当前待办与未解决问题编写 spec。
- 本轮追加要求：由 `gpt-6-astra/high` 只读复核，查漏补缺、避免过度设计，修订 spec 并编写执行计划。

## 1. 目标、决定与假设

以 Node 24 收敛工程支持范围，停止为 Node 22.8 维护兼容分支或补充运行证据；在不改变现有路由架构的前提下，分别推进原生 worker 安全边界、Jev 可用性、路由质量与成本验证，以及历史待办的有效状态同步。

- **用户已决定**：放弃 Node 22.8 支持和相关补证待办。
- **本草案明确采用的解释**：最低运行版本为 `>=24.0.0`，必需运行验收使用实际 Node `24.x`；不锁定单一补丁版本。高于 24 的版本不因此获得新的验证矩阵，也不能替代 Node 24 验收。若用户要求严格限定 `24.x` 而非最低版本 24，应在批准前调整此契约。
- **本次授权范围**：复核、修订本规格、编写待批准的执行计划和更新待办理解，不实施代码、变更宿主环境、安装依赖、启动付费链路或 commit/push。
- **完成定义**：工程迁移、诊断步骤完成、核心问题解决、成本收益成立是不同结论，必须分别提供证据。外部服务不可用或证据不足时保留未解决状态，不以“额度用完”或“已写报告”代替验收。

本规格补充原 [task-entry design](2026-10-05-turnhelm-task-entry-design.md)，只取代后续实施时的现行 Node 版本承诺及相应兼容补证要求。历史 Node 22.8 测试结果、既有诊断记录及原规格的其余契约不被重写。

## 3. 方案比较与推荐

| 方案 | 收益 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| A：先收敛 Node 24，再按证据门槛分工作流推进 | 最小工程改动，保留既有架构，区分本地缺陷和外部依赖 | 核心问题可能因外部证据不足保持未解决 | **推荐** |
| B：只做 Node 24 迁移，其余事项另行立项 | 工程范围最小、快速结束版本迁移 | 不覆盖本次“基于上述”的三个核心问题和状态同步目标 | 可作为拆分执行方式，但不是整份规格的完成定义 |
| C：直接改造全局 shell、认证/代理策略或引入新路由/观测框架 | 理论上可增加控制面 | 机制未定位、扩大权限和兼容面，可能破坏认证或掩盖真实原因 | 不采用 |

采用 A，按独立工作流分阶段验收。**N24-01…05 成立即可独立验收和交付 Node 迁移**；NAT/JEV/CAL/META 未授权、缺少受支持接口或外部受阻，不阻止这项工程交付，也不据此关闭其核心问题。发布/合并仍需独立授权。

本文件是收敛规格，不要求一次跨模块改造：先写 Node 工程实施计划；其余工作流只列有停止条件的调查调度，发现可修复根因后再提出对应的最小修复计划。

## 4. Node 24 运行与验证契约

### 4.1 版本要求

1. `package.json.engines.node` 为 `>=24.0.0`。
2. doctor 的 `NODE_FLOOR` 为 `[24, 0, 0]`，升级提示为 Node 24 或更新版本；Node 检查与包声明一致。
3. 低于 24 的版本退出支持范围。doctor 的版本项应失败，不提供兼容降级。可以用合成版本边界做负向测试，不安装或执行 Node 22.8 来补证。
4. Node 版本检查只证明满足最低版本门槛，不证明模型授权、Codex 配置语义或所有宿主安全策略。
5. CI 继续使用实际 Node 24，记录实际补丁版本；本地验收必须显式选择 Node 24 执行文件及启动路径，不以当前默认 Node 26 运行结果替代。启用内置环境代理的验收须使用 `24.x` 且 `>=24.5.0`；这是测试能力要求，不将产品门槛改成 24.5。
6. 不改用户的全局 Node 默认值、shell 启动文件或其他项目配置。若缺少 Node 24，记录环境前置条件未满足，在获得安装授权后再验证，不自动安装。

### 4.2 测试与说明收敛

- 删除 `test/direct-transport.test.ts` 的 `NODE_22` 个人绝对路径、专属测试和缺少该二进制时的跳过分支；只删除随之失去用途的导入。
- 保留当前进程的代理测试。对 `NO_PROXY` 不存在和空字符串两种既有场景，在相同受控子进程环境中先用普通默认 agent 的 HTTP 请求证明代理 sentinel 收到请求，再验证生产 direct 请求到达目标 fixture，且代理请求**增量为零**；正向对照与生产请求分别计数。TLS 验证断言不削弱，不添加有效 bypass 列表等无关矩阵。
- Node 24.0…24.4 没有该内置代理能力：可以继续验证其 direct 请求边界，但不得宣称已测试“代理实际启用”。必需的激活验收使用上一条规定的 24.5+，不能跳过或只设变量。该能力及 `Agent.proxyEnv` 的引入版本见 [Node 24.11 Agent 历史](https://nodejs.org/download/release/v24.11.0/docs/api/http.html#new-agentoptions) 和 [内置代理说明](https://nodejs.org/download/release/v24.11.0/docs/api/http.html#built-in-proxy-support)。
- 旧版本专属用例的移除属于**有理由的退役**，不是修复它、执行它或提高测试通过率。报告列明退役用例、新增断言、当前分母及所有跳过理由，不固定沿用 364 这个历史分母。
- README、共享 `turnhelm-routing` skill 和 doctor 使用相同版本要求。修改 skill 时使用 `skill-creator`；元数据只有实际受影响才改，现有共享/符号链接结构不复制为第二份实现。
- 新增现行验证记录；旧日期的验证结果保持原样。旧文档若包含仍被当作现行要求的段落，添加“已被本规格/新验证记录取代”的说明，不篡改旧结果。
- 已安装项目中的旧 skill 若产生内容冲突，沿用现有拒绝覆盖/归属核验行为，由所有者授权协调；不为本次迁移新增自动升级器。
- 保留 pnpm 10.12.1、现有锁文件和依赖；不顺带升级 TypeScript、类型包或分类器依赖。

## 5. 原生 worker 环境与 managed marker

### 5.1 不改变的安全承诺

既有 `subprocessEnvironment` 剥离四项分类器控制及 `NODE_V8_COVERAGE`，`workerEnvironment` 设置 `TURNHELM_MANAGED_CHILD=1`。这是**初始子进程环境**契约，不是 shell 启动、文件系统或所有后代秘密隔离承诺。

不得为了让检查变绿而更换全局 HOME、认证、shell 配置、代理或有效沙箱策略；不得把清空全部环境当作通用修复而破坏 Codex 正常认证。

### 5.2 诊断证据

1. 先锁定当前版本的可信执行器/工具来源和可支持的观测接口，再定义一次有限的只读观察。模型自然语言自述不能单独作为工具执行证据。
2. 分别记录初始 spawn、实际工具调用边界、目标 shell 后代；不可混为一个“worker 环境”。shell 可执行文件、登录模式、目标工作目录是否匹配、有效策略来源，只在可信元数据实际提供时记录；不可由缺少 marker 倒推出模式或归因。
3. 分类器控制和 marker 只记录允许名单下的存在布尔值/`markerEqualsOne`；不读或保存密钥值、完整环境、认证内容或启动脚本内容。合成哨兵优先，新夹具不得新增完整宿主环境写盘。
4. 没有可信来源的字段标为未验证。任何历史观察仍是历史观察，未复现不等于已修复。
5. 只有复现了机制且证明存在可由项目修复的边界，才设计最小 per-worker 修复并做故障敏感回归；外部执行器不提供必要控制时，保留依赖阻塞，不猜测设置。

| ID | 必需证据 |
| --- | --- |
| NAT-01 | 四项初始控制剥离、coverage变量隔离、marker、认证路径和真实 worker 参数等原有断言仍成立 |
| NAT-02 | 新观察具有版本/工具/请求归属，初始与后代结果分开，安全投影无任意字段/值，记录为一次真实观察而非模型叙述或假 worker |
| NAT-03 | 核心问题关闭必须有因果机制与对应修复验证，或证明先前结论无效的直接证据；可信来源不足时仍未解决，不能只关闭诊断任务就关闭核心问题 |

本工作流不执行旧真实环境 dump 恢复、擦除证明或自动密钥轮换。此类操作须另行安全授权。

## 6. Jev 可用性与响应前失败

1. 先核验可支持的可信观测来源，再运行既有本地合成 fixture 验证传输和脱敏。当前 `directChoiceRequest(spec: RequestSpec): Promise<unknown>` 没有阶段 observer，request error 被收敛为固定错误，`TaskAttempt` 也不含阶段；不能凭现有 receipt 区分 DNS/连接/TLS。缺少来源时记录 unknown，不为调查预建 observer、错误分类器或框架。新增诊断代码只有在机制明确、范围最小且另行批准后才实施。
2. 后续真实观察只能使用受支持的既有 Jev 接口；不猜测 endpoint、不加代理/VPN/TLS绕过、不轮换认证或自动重试。
3. 安全证据限定为当前提交/Node版本、时间、后端、客户端调用次数、受信事件来源、失败阶段/有限类别、已观察的 HTTP 状态、是否存在响应和可安全保存的关联信息。HTTP 状态未知必须为空，不能填451。
4. 可信观测若确实支持，可记录 DNS、连接、TLS、超时、取消、HTTP 状态、响应读取/解析；不要求凑齐所有类别，不能由通用错误倒推。原始错误字符串、响应体、认证头、任意响应头和完整请求不写盘。
5. 客户端发起、服务端接收、完成推理、产生计费是不同事实；没有服务端证据时不得推断后几项。
6. 服务方状态/时间/关联证据与本地传输观察对照后，才确定本地缺陷或外部依赖。451本身不证明地域、法律、账号或某个中间层原因。
7. 真实失败即停止本次链路，不自动改配置重试。不得用 npm registry 的 DNS/审计结果解释 Jev。

| ID | 必需证据 |
| --- | --- |
| JEV-01 | 既有传输脱敏、超时/取消、无重试及安全回归通过；记录实际可支持的观测字段，不支持阶段归因时为 unknown；无端点/代理/认证变更，不强制新增诊断 API |
| JEV-02 | 获得可审计的新归因证据；响应前失败不被描述为再次451，不能证明原因时保留未验证/外部依赖阻塞 |
| JEV-03 | 宣称链路恢复时，在另行授权的有限新验证中获得成功分类，以及该声明范围所要求的真实只读 worker 结果；仅 doctor/probe 成功不等于完整任务成功 |

归因与恢复分别验收；外部问题未恢复，核心可用性问题仍未解决。

## 7. 路由质量、时延与成本

### 7.1 冻结实验设计，而非先调 rubric

- 复用原六档自然路由，不按提示长度、文件数量、某个关键词或已知结果强制档位；不新增 force-profile、max 特权出口或执行中换模型。
- 在任何新实测前冻结非敏感中英任务、开发集/独立留出集、task hash、机器可判的质量 oracle、可接受 profile 集合、基线配置、候选配置、运行顺序及预算。
- 同一案例的基线与候选拥有相同输入与验收条件、独立项目/run_id；执行前冻结顺序，失败仍纳入数据，不补跑或排除失败来制造优势。小样本可交替基线先/候选先降低顺序偏差；仍不能据此宣称统计显著。只有需要且授权的任务才可使用 `--write`。
- 基线是事先认可的 model/effort 组合，候选是现有自然路由。推荐在专属基线项目通过现有六个 profile 配置统一绑定该组合，仍走正常 `run`；候选项目保留其冻结配置。不得改用户生产配置或为实验新增产品执行旁路。
- 当前 schema 允许六个 ID 绑定同一合法 model/effort，不要求绑定不同；配置必须通过现有校验，真实模型准入仍需独立证据。该基线同样经过分类器，不等于直接 Codex、绕过分类器或零分类开销的基线。
- 每次正常 `run` 仍只启动至多一个 worker。多案例/对照实验的总调用数必须计入单独授权额度，不能借“每次一个”绕过整体上限。
- 调整规则只能使用开发集；调整后冻结新版本，再验证未被用于调优的留出集。案例、规则或门槛改变必须形成新实验，不重写旧成绩。
- 未发现需要调规则时不安排调优循环。首次真实失败终止本轮对应实验链路，失败保留，尚未执行的配对/案例标为未执行；不得为补齐配对继续调用或将未执行算通过。

### 7.2 指标与结论边界

1. **分类策略集合匹配**、**worker输出质量**、**模型可用性**、**时延**、**可核验成本**独立记录。四例集合匹配不作为一般准确率。
2. 质量不能降级：候选必须通过同一案例所有预先约定的验收/安全条件。基线失败时该案例不能支持“候选不劣”或节省结论。
3. 记录完整任务耗时、所有成功/失败客户端尝试、worker结果和报告的 usage。缺失 usage 用 `unreported`，不填零；输入/缓存/推理子计数不重复累加。
4. 成本比较包括声明范围内的分类器、worker、失败尝试与相关编排开销；只有可归属、同口径的服务/账单证据齐备，才能报该范围的真实金额。未覆盖的成本范围必须注明；不把 ChatGPT 登录 usage 当成 API 账单。
5. 候选通过全部质量条件且同口径总成本严格低于基线，才可对冻结样本宣称成本下降；时延降低另行比较。无账单或范围不完整则成本收益未验证，不由 token 数、选中了便宜模型或未使用 Jev 推算。
6. 小样本只给有限案例结论，不自动推广到全部任务、最轻充分档位、六档普遍可用或一般节省比例。
